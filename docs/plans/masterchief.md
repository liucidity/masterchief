## Overall notes

- Round 1: should be compatible with many models (local ai, claude plans, grok, gpt, etc, with both plans and api)
- Round 2: rename XO to cortana
- Round 4: Round 4 note: replace the HTTP daemon API with commands plus a watcher. No server in v1.

Architecture change:
The Commander is an LLM session in a CLI, as in option A.
It controls the crew through a command-line tool called mc.
mc commands read and write SQLite and the tmux session backend, then exit.
There is no HTTP API and no always-on server in v1.
The package can stay named packages/daemon for now to avoid churn, but it contains no server.

API block change:
Rename the "Daemon commands" block to "mc commands".
Each endpoint becomes a subcommand the Commander calls from its own CLI session.
Proposed subcommands, to be refined in review:
mc spawn: start a crewmate or scout with concrete harness, model and effort.
mc status: show a task's state and its last screen capture.
mc send: steer a task with text, Enter, Escape or interrupt.
mc teardown: remove a task, and refuse if it holds unlanded work.
mc events: print pending wake events.
mc watch: run the watcher.

Watcher (mc watch):
One small background process, started by the Commander's startup instructions.
It polls agent state without calling a model.
Each harness reports busy, idle, unknown or dead.
Unknown is never treated as idle or busy.
It wakes the Commander only when something is actionable: finished, blocked, stale or dead.
If the watcher crashes, crew terminals keep running in tmux.
Restarting it resumes from the SQLite state.

Optional afk mode (mc afk):
A separate optional daemon for when the human is away from the keyboard.
Off by default.
While afk is active, the afk daemon triages wakes instead of the Commander session.
Routine wakes are handled without interrupting the Commander.
Anything that needs a human decision is queued for the human's return.
On return, the human gets a short brief listing what happened and what is waiting.
Details such as exactly what the daemon may decide alone are open questions for review.
This is modeled on firstmate's away mode, which I only read at the header level.

Later:
A TUI or web deck can read the SQLite database directly.
Add an HTTP API only when a live-updating UI needs one.

Also update:
Data model: keep as is, plus a field to record whether afk is active.
Architecture and risks: add the risk that two writers (mc commands and the watcher) share one SQLite file.
Open questions: what quota data source to use, and the plan login terms for personal use.
